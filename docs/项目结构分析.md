# 监控系统项目结构分析报告

## 1. 项目概览

**项目名称**: Server Monitoring System (yw3)  
**技术栈**: C++17 + Python3 + CMake + OpenSSL  
**架构模式**: Agent-Server分布式监控系统  
**代码规模**: ~58个源代码文件，~33K行C++代码  
**最新提交**: 扩展告警指标路径和修复系统稳定性问题

### 核心功能
- 多节点集群资源监控
- 实时告警规则评估
- 告警事件生命周期管理
- Web仪表板可视化
- RESTful API接口

## 3. 分层架构详解

### 3.1 领域层 (Domain Layer)
**职责**: 包含业务核心逻辑、富领域对象和业务规则

**关键组件**:
- **AlertRule** - 告警规则实体
  - 支持复杂的多条件表达式
  - 包含评估逻辑和数据新鲜度检查
  - 属性: ruleId, alertName, expression, severity, isEnabled等

- **AlertEvent** - 告警事件实体
  - 状态机: FIRING -> ACKNOWLEDGED -> RESOLVED
  - 工厂方法模式创建
  - 业务规则: 状态转换的合法性检查

- **MetricSnapshot** - 指标快照
  - 时间序列数据
  - 包含多维指标: CPU、内存、磁盘、网络等
  - 支持标签扩展

- **ServerNode** - 服务节点
  - 表示被监控的服务器
  - 属性: nodeId, hostname, status等

**仓储接口** (依赖倒置原则):
- IAlertRuleRepository - 规则持久化接口
- IAlertEventRepository - 事件持久化接口
- IMetricRepository - 指标数据接口
- IServerNodeRepository - 节点数据接口

### 3.2 应用层 (Application Layer)
**职责**: 编排领域对象完成具体的用例

**核心服务**:

1. **IngestionService** - 数据接收
   - 处理Agent上报的心跳和指标
   - 节点注册和更新
   - 指标数据持久化

2. **AlertingOrchestratorService** - 告警编排
   - 定时评估所有告警规则
   - 检测状态变化并生成告警事件
   - 管理告警的整个生命周期
   - 间隔: 30秒检查一次

3. **AlertRuleManagementService** - 规则管理
   - CRUD操作
   - 启用/禁用规则
   - 批量管理

4. **AlertEventManagementService** - 事件管理
   - 查询告警事件
   - 认知告警 (acknowledge)
   - 解决告警 (resolve)

5. **QueryService** - 数据查询
   - 节点查询
   - 指标查询（按时间范围）
   - 聚合查询

**DTO (数据传输对象)**:
- AlertRuleDTO - 规则传输对象
- AlertEventDTO - 事件传输对象
- HeartbeatDTO - 心跳传输对象
- QueryDTO - 查询条件对象

### 3.3 基础设施层 (Infrastructure Layer)
**职责**: 实现仓储接口、外部服务集成

**当前实现**:
- **Mock仓储** - 内存存储实现
  - MockNodeRepository
  - MockMetricRepository
  - MockAlertRuleRepository
  - MockAlertEventRepository

**计划实现** (根据技术栈):
- PostgreSQL实现 - 元数据存储
- InfluxDB实现 - 时序数据存储
- HTTP适配器 - 外部API集成
- 通知器 - 告警通知 (邮件、钉钉等)

### 3.4 表现层 (Presentation Layer)
**职责**: HTTP接口暴露业务功能

**HttpServer**:
- 基于cpp-httplib库
- 多线程处理并发请求
- 自定义JSON解析器

**API路由**:

```
# 数据接收
POST   /api/heartbeat              - Agent心跳
POST   /api/resource               - Agent上报资源指标

# 告警规则管理
POST   /api/alert-rules            - 创建规则
GET    /api/alert-rules            - 获取规则列表
GET    /api/alert-rules/{id}       - 获取规则详情
PUT    /api/alert-rules/{id}       - 更新规则
DELETE /api/alert-rules/{id}       - 删除规则
POST   /api/alert-rules/{id}/enable - 启用规则
POST   /api/alert-rules/{id}/disable - 禁用规则
GET    /api/alert-rules/active     - 获取活跃规则

# 告警事件管理
GET    /api/alert-events           - 获取所有事件
GET    /api/alert-events/{id}      - 获取事件详情
GET    /api/alert-events/node/{nodeId} - 按节点查询
GET    /api/alert-events/rule/{ruleId} - 按规则查询
GET    /api/alert-events/active    - 获取活跃事件
GET    /api/alert-events/status/{status} - 按状态查询
POST   /api/alert-events/{id}/acknowledge - 认知事件
POST   /api/alert-events/{id}/resolve - 解决事件

# 节点和指标查询
GET    /api/nodes                  - 获取所有节点
GET    /api/nodes/{nodeId}         - 获取节点详情
GET    /api/nodes/status/{status}  - 按状态查询节点
GET    /api/nodes/{nodeId}/metrics - 查询节点指标
```

## 8. 核心业务流程

### 8.1 数据流向
```
Agent (采集器)
    ↓ (HTTP POST /api/resource)
Server (接收服务)
    ├─→ IngestionService (存储指标)
    │   └─→ MetricRepository
    │
    └─→ AlertingOrchestratorService (评估规则)
        ├─→ AlertRuleRepository (查询规则)
        ├─→ MetricRepository (查询指标)
        └─→ AlertEventRepository (保存事件)
            ├─→ NotificationService (发送通知)
            └─→ Frontend (显示)
```

### 8.2 告警规则评估流程
```
1. AlertingOrchestratorService 定时触发 (每30秒)
2. 遍历所有启用的告警规则
3. 对每个规则:
   a. 查询最近的指标数据
   b. 检查数据新鲜度和覆盖率
   c. 调用 AlertExpressionEvaluationService 评估
   d. 根据结果判断是否触发/解决告警
4. 生成或更新 AlertEvent
5. 持久化到 AlertEventRepository
```

### 8.3 告警事件生命周期
```
创建 (FIRING)
    ↓ 
[手动/自动] 认知 (ACKNOWLEDGED)
    ↓
[手动/自动] 解决 (RESOLVED)
```

## 9. 设计原则

### 9.1 架构模式
- **分层架构** (Layered Architecture)
  - 清晰的职责分离
  - 依赖自上而下

- **领域驱动设计** (DDD)
  - 富领域对象 (AlertRule, AlertEvent)
  - 仓储模式
  - 领域服务

- **依赖倒置原则** (DIP)
  - 定义仓储接口 (I*Repository)
  - 接口隔离
  - 易于单元测试和Mock

- **工厂模式**
  - AlertEvent::create() 确保对象创建的合法性

- **状态机模式**
  - AlertEvent 的状态转换

### 9.2 高内聚、低耦合
- 层之间通过接口通信
- 每个组件单一职责
- 易于扩展和维护
